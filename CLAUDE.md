# Slideshot: project guide for Claude Code

Slideshot is an internal tool at 24Slides. Designers send finished PowerPoint slides for review from an **add-in side panel**; Design Managers (DMs) distribute work, review every slide and track each order on a **web dashboard**. There is no dev team: Uda (senior product designer) builds it with Claude. You write the code, read/edit Figma through the Figma MCP, and she reviews by Figma frames and screenshots.

## How to work with Uda
- She writes mostly **Indonesian**, sometimes English. Answer in the language she writes in. **All product UI copy stays English.**
- **Apply Figma designs exactly.** Read the node, measure it, then match px, colors, radius and spacing. Export icons from Figma as SVG; never hand-draw icons. After building, measure DOM positions against the Figma numbers and look at a screenshot. Fonts render ~1px wider in Chrome than in Figma, so give wrapping text 1–2px slack to keep Figma's line breaks.
- If the design conflicts with how something works (e.g. a hover button covering a tag), do not silently pick: apply the design where possible, explain the conflict, propose one fix.
- **Never commit or push until she says "commit".** Commit messages are short English imperatives, e.g. `Fix duplicate positions; show Slide x → Slide y in the header`.
- **Bump `APP_VERSION` in `panel.html`** on every panel change (footer shows it; currently 2.52). The dashboard has no version string.
- **After every shipped change, update the docs**: edit `docs/gen/gen.py` (English and Indonesian together, plus a release-notes row, the version badge and the "Updated" date), run `npm run docs`, and publish/commit `docs/slideshot-docs.html`.
- For each visual change, save a preview PNG (`npm run shot`) and tell her where it is. Say plainly what was only tested with mock data.
- Be honest and short. Report what changed, what you verified, and what she needs to decide.

## Architecture (no build step)
- Static files served by **GitHub Pages**: repo `Ridhoofrahman/Slide-preview-automation`, folder `slide-qa-marker/`. Live base URL: `https://ridhoofrahman.github.io/Slide-preview-automation/slide-qa-marker/`. Pages deploys ~1 minute after a push.
- Backend: **Supabase** (project URL is in `slide-qa-marker/config.js`; the anon/publishable key there is public by design). **Sign in with Slack** (provider `slack_oidc`, implicit flow; dashboard redirects to `REVIEW_PAGE_URL`, the add-in opens `auth-slack.html?code=…` in the **system browser** (`openBrowserWindow`; Slack refuses Office's embedded dialog on Mac) and polls the Edge Function `login-handoff` for the session), with email + password kept as a fallback link. **Sign-ups are on, for @24slides.com only:** the first Slack sign-in creates the account; the Auth hook "Before User Created" (`public.hook_slideshot_signup`, `sql/signup-hook.sql`) rejects any other email; Confirm email stays on. An account that already exists (e.g. created by an admin) is matched by email. A new designer picks their team once after the first sign-in; a DM on `dm_allowlist` gets DM access and their team from the first sign-in. Only **members** use the data: DMs, designers on **`designer_allowlist`** (110, from Inner Platform; listed designers get their team automatically) and DMs on `dm_allowlist`. `public.is_member()` decides; restrictive "members only" policies (`sql/members-only.sql`) enforce it on every data table and the `slides` bucket. The panel calls `is_member` after sign-in (`afterSignIn`) and signs a non-member out with a message (fails open if the function is missing); the dashboard is DM-only anyway. SQL: `sql/designer-allowlist.sql` (step 1, lists who would lose access), then `sql/members-only.sql` (step 2). Postgres tables, private storage bucket `slides`, realtime.
- `taskpane.html` and `review.html` are **loaders**: they `fetch` the real app (`panel.html` / `review-app.html`) with a cache-busting `?v=` and `document.write` it, to bypass GitHub Pages' 10-minute cache. **Edit `panel.html` and `review-app.html`, not the loaders.** Exception: `taskpane.html` carries its own copy of the loading screen ("Loading Slideshot…" + the sign-in band looping, `LOGIN_BAND` data copied from `panel.html`); keep the two in sync. In `panel.html`, `#loadView` shows the same loop (`playLoginBand(band, true)`: 2 s rise, 0.6 s hold, 0.2 s fade) until the first real view calls `doneLoading()`, continuing the loader's phase via sessionStorage `slideshot.loadT0`.
- The add-in manifest (`manifest.xml`) points at `taskpane.html`. Users must reinstall only when the manifest changes (name, icons, URLs); app updates reach them when they close and reopen the panel.

## Data model (Supabase)
- `slide_shots`: one row per **version** of a sent slide: `file_key, project (order name), slide_id (PowerPoint's internal id), slide_number (position in the order), alternative_of (null, or the slide number it is an alternative of), total_slides, version, designer, designer_id, team, note, image_path, details jsonb, status ready|approved|changes, reviewed_by, reviewed_at, created_at`.
- `shot_comments`: `shot_id, author, author_id, body, x, y (pin), audio_path, audio_duration, resolved`.
- `project_status`: `key, name, sent_at, sent_by` (the "sent to customer" marker).
- `slide_assignments`: the DM's **distribution**: `order_key, order_name, assignee_id, assignee_name, assignee_team, slides int[], deadline timestamptz (per designer per order, required in the dialog; `sql/deadlines.sql`), created_by, created_team`.
- `slide_files`: one row per sent slide (latest version only; unique `file_key, slide_id`): `order_key` (digits), `project, slide_number, alternative_of, shot_id, version, storage_path, size_bytes, team, uploaded_by, uploaded_at`. File in bucket `slide-files` at `<order digits>/<user id>/<file_key>_<slide_id>.pptx` (upsert: a new version replaces it). Designers write only for orders they are assigned in (`can_upload_slide_file`) and read their own; DMs read all and delete; members only.
- `profiles` (`user_id, name, team, slack_user_id`), `design_managers` (`user_id, from_allowlist`).
- `notification_queue`: one row per (event, recipient); RLS on with no policies (service role only). Filled by triggers on `slide_shots` and `slide_assignments` (`sql/notifications.sql`), sent by `notify-slack`. Spec: `docs/specs/slack-notifications.md`.
- **DMs come from table `dm_allowlist`** (`email, name, team`; 24 DMs, one per team, from Inner Platform; no client access). Triggers on the list and on `auth.users` insert keep `design_managers` and `profiles.team` in sync, so a listed DM is a DM with the right team from the first sign-in and never sees the team step; removing an email removes only `from_allowlist` rows (manual admin DMs stay). SQL: `sql/dm-allowlist.sql`.
- A person's **team comes from `public.profiles.team`** (both apps; later from Inner Platform). Account `user_metadata` holds `{name, team}`, but its team is only a copy for old clients and is never read. One team per person. The list lives in table **`teams`** (`name` pk, `office`, `active`; Indonesia + Peru, spelling matches Inner Platform, e.g. **Avvenger**; read-only for clients, edited in SQL; later synced from Inner Platform). The two team `<select>`s (`#dmTeam` in `review-app.html`, `#teamStep` in `panel.html`) are filled by `fillTeams()` from active teams grouped by office; the email forms have no team field (a user with no team gets the team step after signing in). `profiles.team` is a nullable FK to `teams.name` once `sql/profiles-team-fk.sql` has been run.
- RLS today: only **members** (`is_member()`: DMs and listed designers) read or write anything, via restrictive policies on top of the rest, once `sql/members-only.sql` has run; among members, everyone reads every order; writes that matter (review, comments, delete, status, distribution) are **DM-only** via `is_dm()`; designers can insert their own slide_shots. A stricter per-team design exists in `sql/teams-setup.sql` (parked, not applied).

## Rules the code implements (find them before changing them)
**Orders.** An order is identified by its **digits**, any length: `123`, `#123`, `Order #123` are the same (`orderId()` in both files). The panel stores `Order #N` (`canonicalOrder`), shows `#N` (`shownOrder`), types a `#` automatically (`hashAsYouType`), and, once the DM's distribution is found, **adopts the DM's spelling** (`order_name`) so everyone's slides land in one order. The dashboard merges distributions under the matching order in `buildIndex()`.

**Panel start (`askOrder`).** First open of a deck asks "Which order is this?" (saved in the .pptx via `docStore`, keys `slideqa.orderSet|project|fileKey|workfile|map`). The order must have a distribution, otherwise "We can't find this order…" (fail-open if the lookup errors).

**Assignment tags.** `render()`: slide mine → "Assigned to you" (+ two icon buttons: change position, note); someone else's → "Assigned to Name_Team" (read-only); unassigned, or order not distributed → header tag **"Not to work"** and no buttons. Unsent assigned slides show the **"Not sent yet"** tag.

**Same Order ID, different deck.** Detected by comparing the file's slide ids with ids already sent for that order. A genuine clash blocks sending ("Order ID has already been used"); a designer who is *assigned* in that order is treated as working in a new file instead (purple note on the order step, `workfile` flag).

**Working file.** Slides of a new file are mapped, in order, onto the positions the DM assigned (`applyWorkingMap`). Manual picks come first.

**Positions** (`sentPositions`, `applyWorkingMap`, `openMapPop`, `setPosition`). The DM sees a slide at the position of its **latest sent version**. The popup's "Sent as" list contains only the designer's assigned positions; a position held by another sent slide is **disabled** ("Slide 4 · sent"), so two slides can never share a number. A sent slide may move; the new position applies from its next version. Header shows `Slide 9 → Slide 4` when moved. Unsent slides swap with a displaced slide.

**Alternative slides** (v2.42; Figma 478:15576, 479:15630; `sql/alternatives.sql`). A designer marks a slide as an alternative of one of their assigned slides (button `#altBtn` on unassigned or own unsent slides, popup `#altPop`, choice saved in `docStore` key `slideqa.alt` until sent; after that `slide_shots.alternative_of` decides). An alternative holds no position: `applyWorkingMap` takes alternatives out first and numbers the other slides without them (`x.deck` = place in the file, `x.local` = number among normal slides), so an alternative inserted mid-deck does not shift the rest. Alternative rows store `slide_number = alternative_of`. Label `1a`, `1b` = order of first send per slide (`altLabel` in the panel, `slideLabel` on the dashboard). Header "Slide 1a", purple Tag "Alternative of slide 1" with × (only before sending), note button, button "Send as alternative of slide 1". Dashboard: alternatives at the end of the strip; skipped in `projectProgress` (ring, Send to customer). Protocol for designers: put alternatives at the end of the deck. Slack: "sent an alternative of slide 1"; the link adds `&alt=1`.

**Compare with original** (v2.44; spec `docs/specs/compare-with-original.md`, Figma 541:4724). Bar `#cmp` in the dock above the footer, shown on my slides and alternatives **before sending only** (`notsent` / `update`). The designer picks the customer's .pptx once per order; only its extracted text is stored, in IndexedDB `slideshot-compare` / `originals`, key `order:<id>` (never in the .pptx, never uploaded). A check exports the active slide (`exportAsBase64`) and compares it with original slide `cur.n` (alternatives: `cur.alt`). Switching slides collapses the bar; the trash icon (Builder DS `trash-can`) removes the original. Missing text carries an anchor (`after`/`before` + the matching slide text) shown as "After “…”" with a bullseye that selects that text. Blocks are sorted in reading order (top, then left) when every shape has a position, else file order. Unpaired slide text shows as **Added text** (last section per location; not counted in "n differences", status adds "· n added"). Pairing similarity = max(word Dice, letter-pair Dice with spaces ignored, ≥8 letters), threshold 0.5. Bullseye (searches inside groups via `shape.group.shapes`, PowerPointApi 1.8; older Office: top level only): `TextRange.getSubstring().setSelected()` for text, `setSelectedShapes` for tables and charts (cell text can't be selected), none for notes. Copy: `navigator.clipboard`, fallback `execCommand`. Never blocks sending. Spike results (Mac + Windows) in the spec, section 9b.

**Slide files for compile** (v2.50, phase 1; the compile itself is not built). After `markReady` inserts the shot, `saveForCompile` uploads the one-slide .pptx that `readDetails` already exported (`exportAsBase64`, no second export) with an XHR POST to Storage (`x-upsert`, progress), then upserts `slide_files`. Never blocks or fails sending. Row `#cfile` under the actions: Saving for compile… n% / Saved for compile / Not saved for compile. Retry (two quiet retries at 4 s and 12 s first; Retry re-exports the slide as it is now) / Too big (> 50 MB). Sign out aborts uploads (`stopFileUploads`). Slides sent before `FILES_SINCE` show nothing. The dashboard deletes the files with their slides: `removeShots` (by `shot_id`, before the shots go), `deleteProject` (also by `order_key`, own team on tag team) and `sweepSlideFiles` on every dashboard load (rows whose `shot_id` was cleared, e.g. by an older dashboard tab). All through `dropSlideFiles`; errors are only logged. Mock: `?file=fail|slow|missing`.

**Compile an order** (v2.51, phase 2). Dashboard: "Compile order" (card menu + review header, only when `allSlidesApproved`: every strip slide incl. alternatives approved) → `downloadCompileStarter` fills `{{ORDER}}` in `assets/compile-starter.pptx` (JSZip from cdnjs) and downloads "Order N - compile.pptx". The starter's first slide has a title shape named **"Slideshot compile"** reading "Compile Order #N" (the marker; works on every platform) and an add-in part for Slideshot with `Office.AutoShowTaskpaneWithDocument` (auto-opens on Mac only; on Windows the DM opens Slideshot). Panel: `enterApp` → `detectCompile` → `enterCompile` (DMs only) → `compilePlan` blocks unless every slide is approved, every assigned position is sent, no position is sent twice and every slide has a `slide_files` row of the latest version → `runCompile` downloads each file and `insertSlidesFromBase64` (KeepSourceFormatting) after the previous one, normal slides by number then alternatives (1a, 1b…), then deletes the starter slide; a failure stops with "Try again (continue from slide N)". Mock: `/panel?compile=ready|blocked|dlfail&dm=1`. Verified in real PowerPoint for Mac on 2026-11-24 (auto-open, order, alternatives, fonts/charts/animations, no extra masters, starter removed); Windows not tested yet. A slow connection can leave the pane blank for a while before it loads.

**Tag team.** An order is tag team when slides or distributions involve more than one team. Each DM can decide (approve / request changes) only on **their own team's** slides (`canReview`); both see the whole deck. Designer filter chips on the review page appear when 2+ designers work on the order.

**Board tabs and Distribution** (Figma 483:18468 board, 465:14440 + component "Load distribution" 483:16733, dialog 483:19733). Tabs "Assigned orders" (the order cards) and "Distribution" (`BOARD.view`, saved in localStorage `qa.view.board`). Distribution: one card per designer of the DM's team (`teamDesigners()`: `profiles.team` = my team, not in `design_managers`), rows = their assignments: order, slide chips, approved/assigned (normal slides only), deadline (red overdue, yellow < 2 h, grey; "Completed" when all approved). Overdue first, then nearest deadline. Assign order dialog: one row by default, × only from the second row, deadline required (browser date-time picker behind a "Today, 14:00" field, `dueField`), blurred scrim backdrop.

**Dashboard access.** DM-only (`isDesignManager`, reads `design_managers`; fails open if the table is missing so nobody is locked out during setup). The add-in footer (Figma 412:11104) shows name and team; a click opens a second row with an **Open dashboard** link (DM accounts only), the version and Sign out. A designer view is planned (see open items).

**Progress.** The ring counts approved vs **sent** slides only. All approved shows a full ring; after "Send to customer" the ring is solid green with a check. "Send to customer" only marks status inside Slideshot; it does not email or notify anyone.

**Slack notifications** (`sql/notifications.sql`, `notify-slack`; spec `docs/specs/slack-notifications.md`). Events: `slide_sent` / `slide_revised` to the DMs of the slide's team, `assignment_changed`, `changes_requested`, `approved` to the designer. Batched per recipient + order + event (+ designer for DM events): 3 / 1 / 5 min. Never about your own action (`auth.uid()` = recipient). Privacy: order number, slide numbers, counts, names and a link only. Deleting an order notifies nobody (sender sees no distribution left). Decisions undone within the window are dropped at send time. Status 19 Nov 2026: **live** (bot token and `DRY_RUN=false` set; tested on Uda's account). The function code in Supabase is pasted by hand: after changing `index.ts` or `messages.ts`, redeploy it (one file, `messages.ts` inlined). DM messages link to `review.html?order=N&slide=M` (`stashDeepLink` / `openDeepLink`: query string kept in sessionStorage through the Slack sign-in; never the hash).

**Retention.** Orders are removed 30 days after last activity (`RETENTION_DAYS`, `cleanupOldProjects`, at most once a day per browser). Deleting an order also deletes its distribution; on a tag team order a DM deletes only their own team's slides.

## Design system

Use its **Mapped** colour tokens (`text/*`, `icon/*`, `background/*`, `outline/*`, `elevation/*`), **`scale/*`** spacing, `radii/*`, `text-*` styles, `Shadow/*` styles, components (Button, Button Icon, Tag, Fields, Dropdown, Tooltip, Checkbox, Tab…) and `Icon/regular/*` icons. In Figma, import from the library (`search_design_system` with the Builder DS library key) and bind variables; do not use raw hex. If the DS lacks something, say so and propose an addition. ## Develop and test
```bash
npm install                      # only needed for screenshots (Playwright)
npx playwright install chromium
npm run dev                      # test server on http://localhost:5173
npm run check                    # syntax check of every inline script
npm run shot -- "/panel?n=1&st=notsent&dm=1" out.png --w 320 --h 694
npm run shot -- "/review" board.png --w 1280 --h 760 --wait 2500
npm run docs                     # regenerate docs/slideshot-docs.html
```
- `/panel` runs the real `panel.html` against `dev/mock-panel.js` (fake Office.js + Supabase). Query params: `n` selected slide (1-10), `st` = `notsent` | `waiting` | `update` | `seed` (slides 8 and 9 already sent), `dm=1` makes the account a DM. In the page, `window.__sel = 8; refreshDeck()` switches slides.
- `/review` runs the real `review-app.html` against `dev/mock-review.js` (five sample orders: tag team, single slide, all approved, sent to customer, distribution only).
- Not covered by the mocks: real Office.js timing, `slide-details.js` (it needs a real .pptx), real Supabase RLS. Uda tests in real PowerPoint and reports back. Verify risky logic by reading the code paths, then say what was not run for real.
- The pages are single files with one big stylesheet each. **Grep a class name before inventing one** (`.bd-top` is already the dashboard's sticky top bar; reusing it once broke the new card layout).
- When screenshotting after a scroll, disable smooth scrolling first (`document.documentElement.style.scrollBehavior='auto'`).

## Release
1. `npm run check`, then test in the browser with the mocks.
2. Commit and push to `main` (the repo belongs to the `Ridhoofrahman` account: you need write access, or a fork).
3. GitHub Pages updates in ~1 minute. Designers close and reopen the panel; the version shows in the footer.
4. If `manifest.xml` changed: everyone runs the installer again (it closes PowerPoint, asking to save first):
   - Mac (Terminal): `curl -fsSL https://ridhoofrahman.github.io/Slide-preview-automation/slide-qa-marker/install/install-mac.sh | bash` (puts `slideshot.xml` in `~/Library/Containers/com.microsoft.Powerpoint/Data/Documents/wef`).
   - Windows (PowerShell): `irm https://ridhoofrahman.github.io/Slide-preview-automation/slide-qa-marker/install/install-windows.ps1 | iex` (saves `%LOCALAPPDATA%\Slideshot\slideshot.xml`, registers it under `HKCU\Software\Microsoft\Office\16.0\WEF\Developer`, clears `%LOCALAPPDATA%\Microsoft\Office\16.0\Wef`).
   - Then Insert > Add-ins > My Add-ins > Developer Add-ins > Slideshot. The shared-folder install still works as a fallback.
5. Update the docs page (see above).
